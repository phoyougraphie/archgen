# Décisions d'architecture

| ID | Décision | Motif / conséquence |
|---|---|---|
| ADR-01 | Génération hybride C : plan indépendant + writer SketchUp | Le fil a retenu cette séparation. Shell et Structural partagent les solveurs de placement. Interior est réservé. |
| ADR-02 | Trois profils actifs ; 24 fiches ; sept familles techniques | Le fil retient Haussmannien, Toulousain et Brutaliste. Les autres restent désactivés tant que leurs capacités et tests n'existent pas. |
| ADR-03 | Configuration V1 fermée, valeurs effectives figées et conservées ; saisie séparée | La réouverture ne recalcule pas de valeurs implicites. Changement de style = transition explicite. |
| ADR-04 | Une racine top-level par bâtiment, définition de remplacement fraîche | L'identité de l'instance, sa transformation et les copies restent stables. Pas d'édition imbriquée en V0.1. |
| ADR-05 | Subdivision explicite et jonctions à onglet, quatre pièces murales fermées | Évite les booléens SketchUp et les chevauchements volumétriques. La racine n'est pas un solide unique. |
| ADR-06 | Unités m/rad au calcul, degrés en saisie/JSON de config | Les champs portent leurs unités ; une seule conversion à chaque frontière. |
| ADR-07 | Aperçu 2D en dialogue, sans écriture | Même vérité géométrique, rapide, aucune trace dans l'Undo. |
| ADR-08 | Cible initiale Desktop 2024–2026, Ruby compatible 3.2, Windows et macOS. **Remplacée par ADR-26** | Minimum fondé sur Ruby embarqué documenté. Matrice à vérifier dans les versions réellement disponibles ; aucune compatibilité annoncée avant la recette. |
| ADR-09 | API minimale et géométrie locale ; pas de purge globale | Réduit les conflits avec les autres extensions et protège les ressources utilisateur. |
| ADR-10 | Migrations de format distinctes des changements de règles | Une migration adapte les données ; une mise à niveau d'un profil peut changer la géométrie et requiert une régénération choisie. |
| ADR-11 | Code `E_PLAN` pour tout invariant de plan violé, en plus de la liste initiale | Le contrat exige de refuser un plan invalide sans lui attribuer de code. `E_PLAN` signale une anomalie interne : `path:"/plan"`, identifiant de pièce en `params.id`. Aucune écriture. Liste mise à jour dans CONFIG_SCHEMA. |
| ADR-12 | `E_PROFILE_UNAVAILABLE` sur `/lod` tant que les détails n'existent pas | LOD 1 est refusé par le moteur jusqu'à AG-015 plutôt que d'émettre un plan sans détails : pas de réglage silencieux. Les fixtures LOD 1 ne sont générables qu'à partir de cette porte. |
| ADR-13 | Copie embarquée de `schemas/`, `examples/profiles/` et `materials.v1.json` dans `archgen/`, identité vérifiée par test | Le RBZ ne contient que `archgen.rb` et `archgen/`. `composition.rb` est le seul lecteur de fichiers du noyau. |
| ADR-14 | Ressources ARCHGEN marquées par `archgen.resource` : matériaux « ARCHGEN <libellé> », tags ARCHGEN Murs, Dalles, Toiture et Détails sur les seuls conteneurs de premier niveau | Réutilisation seulement si marqueur, révision et couleur concordent ; un homonyme utilisateur reste intact et ARCHGEN prend un nom suffixé. Le writer refuse les définitions partagées jusqu'à AG-015. |
| ADR-15 | Le writer masque les arêtes entre deux faces coplanaires de même matériau d'une même pièce (ex-D-02, choix du propriétaire) | Constat en H02 : la grille de découpe traversait les façades. Les arêtes restent dans la topologie : plan, faces, pièces et volumes inchangés, `ENGINE_VERSION` inchangée. Contours, baies et onglets restent dessinés. Une arête masquée reste affichable avec « Géométrie masquée ». |
| ADR-16 | Marqueur de définition `archgen.definition` non autoritaire ; une création depuis un contexte d'édition est refusée par `E_TARGET_STALE` ; `E_WRITE` ne transporte le message d'erreur que pour les `WriteError` | La configuration vit uniquement sur l'instance. Le message d'une exception native peut contenir des chemins personnels. La racine reste Untagged : seuls ses conteneurs portent un tag. |
| ADR-17 | La référence de cible porte PID, identifiant de définition, révision et empreinte de configuration ; `UI::TargetTokens` les masque derrière un jeton opaque borné à 64 entrées | Le service relit et compare tout avant d'écrire, sans croire le jeton. L'identifiant de définition est son `persistent_id`. La régénération ne renomme pas l'instance : `config.name` reste le libellé du panneau. |
| ADR-18 | Le document se reconnaît à `Model#guid` : jetons et cibles y sont liés, le service le contrôle avant toute lecture | Mesuré en H07 : sous Windows, l'objet `Model` reste égal et valide d'un document à l'autre, et un PID peut coïncider. Enregistrer change le `guid` et périme donc la cible : le panneau recharge la sélection (AG-017). |
| ADR-19 | `TransactionGuard` tient toute écriture : opération jamais imbriquée, abandon unique, relevé avant et après abandon | Un écart après abandon donne `restore_incomplete`, incident bloquant sans opération de réparation. Une exception hors `StandardError` ne laisse pas d'opération ouverte. Un moteur ou un catalogue plus récent rend le bâtiment consultable mais non régénérable (`E_VERSION`). |
| ADR-20 | Code `W_DETAIL` pour un détail demandé mais sans emplacement ; corniche sur toit plat débordant refusée (`E_ROOF_GEOMETRY` sur `/features/cornice`) ; LOD 1 ouvert par AG-015, levant le refus d'ADR-12 | Le contrat demande un avertissement sans en nommer le code : `W_HISTORICAL` aurait menti sur sa cause. Le dessus de corniche serait coplanaire à la rive du toit, ce que le contrat interdit. Le plan LOD 0 reste inchangé, donc `ENGINE_VERSION` aussi. |
| ADR-21 | Messages français dans `UI::Messages`, indexés par raison ; un test vérifie que chaque raison émise a son texte. `archgen/ui/panel_logic.js` isole la logique pure, testée sous Node en CI | L'interface affiche les décisions du noyau sans les reproduire. Le dédoublonnage des messages est un choix d'affichage : les diagnostics restent complets. L'entrée Diagnostic restait au menu en développement ; elle est retirée avec ses fichiers depuis AG-020. |
| ADR-22 | `UI::ConfirmationTokens` : une confirmation active, 120 s, usage unique ; un jeton inconnu ne brûle pas celle en cours. Annuler redemande un aperçu frais. Enregistrer recharge la sélection en gardant le brouillon ; Annuler, Rétablir, sélection et document périment la cible et demandent un rechargement explicite | Observateurs natifs dans `panel_observers.rb`, qui ne font que prévenir : le service revérifie toujours avant d'écrire. Une requête de mutation n'est exécutée qu'une fois par `request_id`. Un enregistrement ne doit pas coûter de réglages à l'utilisateur, alors qu'un Annuler rend le brouillon incertain. |
| ADR-23 | Les recettes hôte du panneau sont scriptées quand c'est possible (`test/host/h10.rb`) : clics DOM, API native, rapport dans `tmp/` ; le pilotage écran reste réservé aux contrôles qui l'exigent | Demande du propriétaire de réserver ce coût aux vérifications importantes. Le script a trouvé deux défauts passés inaperçus à l'écran. Un clic DOM ne prouve pas un clic souris : le rapport le précise. |
| ADR-24 | Le code livré n'écrit aucun journal : le plafond de 100 entrées de SECURITY_PERFORMANCE reste une limite pour un futur journal, sans objet en V0.1. Un test interdit `puts`, `warn`, appels dangereux et réseau dans `archgen/`. H11 mesure la fixture de référence ; le 24 × 18, sans profil nommé au contrat, est mesuré sur le générique et le Toulousain | Le diagnostic passe par le panneau et ne contient ni chemin ni JSON complet : aucun journal n'est nécessaire, donc aucun risque de fuite. Mesurer le profil actif le plus lourd évite une cible tenue seulement sur un cas léger. |
| ADR-25 | Outil cible de l'aller-retour P08 pour H12 : OBJ exporté en mètres depuis SketchUp, importé dans Blender (axes Y/Z, échelle 1). Le produit n'ajoute aucune commande d'export | Blender 5.2 lit l'OBJ nativement sur ce poste et se pilote sans interface. L'OBJ ne porte aucune unité : `units: 'model'` donne un facteur 1 000 dans un gabarit en millimètres, le guide doit donc imposer les mètres. Ce choix ne promet ni autre format ni autre outil. |
| ADR-26 | Cible V0.1 réduite à **Windows et SketchUp 2026** (choix du propriétaire, 2026-11-06). SketchUp 2024/2025 et macOS sortent de la V0.1 ; seule la combinaison testée est annoncée (Windows 11, 26.2.243). Le code reste inchangé : pas de refus au chargement sur un autre hôte, pas d'appel à `manifold?` dans le produit | Ces hôtes ne sont pas accessibles et leur recette bloquait la sortie. Les autres hôtes ne sont ni promis ni interdits, faute de preuve dans un sens ou dans l'autre. Garder le produit sans API récente ne coûte rien et laisse une extension future possible, par une nouvelle décision et sa recette. |
| ADR-27 | D-05 et D-06 tranchées par le propriétaire (2026-11-06), sur la recommandation : **le terrain reste intact** ; ordre : assise d'un bâtiment seul (AG-021 à AG-026), puis EXT-07, enfin l'étagement par parcelle (AG-027) | Non destructif, Annuler trivial, aucun maillage quelconque à fiabiliser. Le remodelage reste possible plus tard, par une nouvelle décision. Le terrain reste visible aux raccords et traverse le bâtiment en cas de déblai. |
| ADR-28 | Assise appliquée à une racine existante, plateforme au point haut par défaut, plan et réglages séparés de la configuration V1, terrain désigné par l'utilisateur ([contrat](TERRAIN_CONTRACT.md)) | Sans découpe, une plateforme à la moyenne enterrerait la façade amont : le besoin d'origine proposait la moyenne, qui reste une option avec avertissement. Le bâtiment se crée à l'origine en V0.1, donc l'assise suit le déplacement au lieu d'exiger un outil de placement. Séparer le format évite toute migration et laisse `plan_digest` inchangé. Deviner le terrain reviendrait à inventer une altitude dès qu'un arbre est présent. |
| ADR-29 | Une racine avec assise la garde quand on la régénère : relevé refait, Z mis à jour dans la même opération ; refus si le terrain n'est plus utilisable, avec le retrait comme action explicite | Écrire une définition sans assise en gardant `archgen.site` serait incohérent, et la retirer en silence perdrait du travail. Conséquence : régénérer après un déplacement réadapte le bâtiment à son nouvel emplacement. |
| ADR-30 | D-03 tranchée par le propriétaire (2026-11-06) : **coupe d'onglet, tous angles permis**. Une parcelle d'angle est un trapèze dont façade et arrière restent parallèles ; une racine d'ensemble porte le tracé et contient une instance par parcelle ([contrat](ENSEMBLE_CONTRACT.md)) | Le tracé reste libre et l'îlot continu. Le parallélisme garde chaque parcelle convexe et permet une toiture en section constante, sans squelette de toit. Le contrat d'emprise rectangulaire reste intact pour un bâtiment seul : le plan de rangée est une voie à part. Un angle trop aigu est refusé d'après la géométrie, pas d'après une liste d'angles. ADR-04 reste valable pour un bâtiment seul. |
| ADR-31 | D-04 tranchée par le propriétaire (2026-11-06) : **forme de l'accès selon le style**. Catalogue séparé `ensemble_rules.v1.json`, par couple profil/révision ; porche pour Haussmannien et Toulousain, interruption pour Brutaliste | Le choix suit l'architecture, sans réglage de plus. Le catalogue séparé évite de réviser les profils publiés. Les deux capacités sont à construire : l'interruption d'abord, le porche ensuite. Une entrée n'est publiée qu'avec sa capacité, et un profil sans entrée ne ferme pas d'îlot. |
| ADR-32 | En rangée, les murs latéraux restent émis en entier et aveugles, dans les deux modes, avec un même gabarit par ensemble (V1) | Le besoin d'origine proposait d'écarter les faces cachées. Les garder laisse chaque bâtiment fermé, sans dépendre de ses voisins, et laissera AG-027 montrer un mur découvert quand deux parcelles sont à des altitudes différentes. Coût : des faces invisibles, mesurées dans le budget. Deux murs Structural mitoyens font une épaisseur double. L'optimisation reste possible plus tard. |
| ADR-33 | Étagement d'un ensemble (AG-027) : **une plateforme par parcelle, racine immobile, assises à part, soubassement seul.** Les parcelles portent le niveau dans leur translation ; chaque assise est une seconde instance de même matrice ; le plan et `ensemble_digest` ne changent pas ; `embankment` est refusé. Le Z de la racine entre dans le calcul et dans le placement enregistré | Les bâtiments restent partagés : sur une pente, seules les assises diffèrent, et le plafond de faces uniques n'en souffre pas. Bouger la racine n'aurait rien apporté, puisque les niveaux diffèrent de toute façon. Un talus déborderait chez le voisin : il faudrait un autre contrat. Choix faits par l'implémentation sur le besoin d'origine et les ADR-27 à 29, sans nouvelle question au propriétaire : à contredire s'ils ne conviennent pas. |
| ADR-34 | Voirie (EXT-11), à la demande du propriétaire (2026-11-07) : **la coupe est la source de la voie**, en format séparé, avec des catalogues fermés de bandes et d'éléments ; le tracé gagne des rayons ; mobilier urbain pur renvoyé à EXT-12. Valeurs de conception, sans vérification réglementaire | Le propriétaire veut d'abord une coupe à l'échelle humaine. Une seule saisie évite de ressaisir les largeurs en plan et en carrefour. Le format séparé laisse intacts bâtiments et ensembles. Les rayons sont une capacité nouvelle : ni route ni rail ne se tracent en lignes brisées, alors que l'ensemble les refuse à juste titre. Choix de structure proposés par le contrat, à contredire sur la maquette. |
| ADR-35 | D-09 tranchée par le propriétaire (2026-11-07), sur la recommandation : **arbres, lampadaires et petit mobilier de voirie en volumes 3D simples à facettes**, couleurs unies, une définition partagée par variante et hauteur. Les composants de l'utilisateur pourront s'y substituer plus tard | Ombres justes, aucune texture, cohérent avec les matériaux unis du projet. Le partage garde le fichier léger : sur une rue plantée, seuls quelques arbres distincts sont décrits. Les plans croisés texturés sortiraient du contrat de matériaux. Mêmes proportions que la coupe de l'éditeur, pour que le plan et la vue 3D se répondent. |
| ADR-36 | D-07 tranchée par le propriétaire (2026-11-07), sur la recommandation : **un réseau par racine ; un carrefour naît tout seul** où deux voies se croisent, où l'une finit sur l'autre, ou où deux voies se rejoignent par leurs bouts. Il est simple par défaut ; son type et son rayon d'angle se changent ensuite au panneau, par un identifiant stable du nœud | Le geste le plus court : on trace, le carrefour suit. Les branches sont connues d'office, et Annuler retire la voie et son carrefour ensemble. Un réseau se régénère en entier, comme un ensemble. |

**Décisions ouvertes** (à trancher par le propriétaire du projet, sans changement de comportement avant cela) :

| ID | Question | Constat et options |
|---|---|---|
| D-01 | Le jitter est-il utilisable tel que spécifié ? | Le contrat tire un jitter par ouverture et refuse deux coupes distantes de moins de 2 mm, sans retentage. Sur la fixture neutre (500 graines), part de graines acceptées : 0 % à 1 cm, 1 % à 2 cm, 16 % à 5 cm, 39 % à 10 cm, 73 % à 30 cm. Tous les profils livrés ont `jitter_m = 0`, donc la V0.1 n'est pas bloquée. **Option A** : arrondir le centre tiré à une grille de 5 mm, les coupes étant alors confondues ou espacées d'au moins 5 mm (recommandée, change le plan des configurations avec jitter). **Option B** : tirer le jitter par travée et non par ouverture, les colonnes restant alignées (moins de variété). **Option C** : conserver le contrat et masquer le jitter du panneau en V0.1. |
| D-11 | Canaux, rivières et fleuves : une coupe comme une voie, ou un objet à part ? | Besoin noté par le propriétaire le 2026-11-07 (EXT-13). **Option A** : un cours d'eau est une voie dont la coupe porte des bandes d'eau, de berge, de quai et de chemin de halage, avec le même éditeur, le même tracé et les mêmes refus (recommandée : tout l'acquis d'EXT-11 sert, largeur variable exclue au départ). **Option B** : un format à part, à largeur variable le long du tracé et aux berges naturelles (plus juste pour une rivière, beaucoup plus de travail). Dans les deux cas, une rivière descend : rien avant D-08. |
| D-12 | Ponts : comment naissent-ils, et lesquels ? | Besoin noté le 2026-11-07 (EXT-13). Un pont exige une voie qui quitte le sol : profil en long, rampes, culées, piles, garde-corps. **Option A** : un pont naît tout seul là où une voie croise un cours d'eau ou une voie ferrée, sur le modèle d'ADR-36, avec un type au choix (poutre, voûte, arc) ; la voie monte et descend par des rampes de pente bornée (recommandée). **Option B** : un objet pont posé à la main, que les voies rejoignent. Dépend de D-08 (terrain) et du profil en long (AG-049). |
| D-08 | Une voie sur un terrain en pente : garder le terrain intact ? | Bloque AG-049. Avec le terrain intact (ADR-27), un fossé ou un déblai resterait **enterré, donc invisible** : le terrain passe au-dessus. **Option A** : terrain intact, voie posée au-dessus, fossés visibles seulement en masquant le terrain. **Option B** : garder l'original masqué et écrire une copie du terrain, entaillée le long de la voie (recommandée : non destructif, fossés visibles, mais une nouvelle capacité sur des maillages quelconques, et une révision d'ADR-27). **Option C** : modifier le terrain lui-même (écarté par ADR-27). Ordre recommandé dans tous les cas : voies horizontales d'abord. |
| D-10 | Que désignent les « clous » du besoin d'origine ? | Bloque seulement cet élément. **Option A** : potelets ou bornes, en place dans la maquette sous le nom Potelet. **Option B** : clous de passage piéton, donc un marquage de traversée. **Option C** : plots ou clous de chaussée, de petits marqueurs sur la voie. |

ADR-03 à 10 précisent les points laissés ouverts dans le fil, avec des choix de départ révisables par décision écrite. Au démarrage, AG-001 consigne les versions hôtes réellement accessibles. Les seuils de performance sont des cibles de livraison à mesurer, et les plages historiques des réglages de conception à calibrer.
