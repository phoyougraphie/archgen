# Configuration et sérialisation V1

Les formats de référence sont [le brouillon](../schemas/building-draft.v1.schema.json), [la configuration effective](../schemas/building-config.v1.schema.json) et [les fixtures](../examples/README.md). Un brouillon est une carte d'overrides ; les champs absents gardent leur valeur de base. Le modèle enregistre uniquement une configuration effective complète. Les nombres de saisie sont des nombres JSON, pas des chaînes ; `null` n'efface rien et est rejeté. Aucune clé inconnue. Hauteurs et longueurs en m, angles de toit en degrés.

| Bloc | Interprétation / vérification transversale |
|---|---|
| `schema_version, name, profile` | Version 1 ; nom UTF-8 non vide après trim ; couple id/révision exact dans l'effectif. Nom par défaut : « Bâtiment ARCHGEN ». Aucun UUID ni placement dans ce JSON. |
| `mode, lod, seed, fidelity` | Shell/Structural ; 0/1 ; entier non signé 32 bits ; strict/plausible/creative. Modes futurs rejetés explicitement. |
| `footprint, levels` | Rectangle ; `count` inclut le RDC ; `heights_m` vide ou de taille count ; non vide remplace `height_m` pour le calcul. Somme ≤ 60 m sous toit ; sommet +/− détails dans le budget. |
| `facade` | `front_bays` s'applique à front et rear ; `side_bays` à right et left, 0 = murs aveugles. `entry_bay` commence à 0 et reste < front_bays. `margin_m` est la marge de trame ; les dégagements réels sont vérifiés par le solveur. `sill_m` est relatif au niveau. |
| `structure` | `wall_m` et `slab_m` restent présents et les mêmes contraintes de placement s'appliquent dans les deux modes ; cette politique garantit le passage Shell → Structural sans repositionner les baies. |
| `roof` | Plat : angles et inset à 0. Deux pans/croupe : `pitch_deg` ∈ [5, 65], autres à 0. Mansarde : `pitch_deg` ∈ [5, 45], `lower_pitch_deg` ∈ [45, 80] et strictement supérieur, `inset_m` > 0, demi-portée restante ≥ 0,2 m. Vérifier l'altitude de rive. |
| `materials` | Trois rôles, plus `glass` avec le vitrage (AG-064) ; seules les clés d'un [catalogue versionné](../examples/materials.v1.json) sont acceptées. Pas de chemins ni URLs. |
| `features` | Booléens pour corniche, balcon, encadrements ; `glazing` facultatif, écrit seulement s'il est vrai, avec `materials.glass` ([détails](DETAILS_CONTRACT.md)). `ground_floor: "shop"` facultatif à la racine, avec `shop.height_m` [3,2 ; 6] sauf si `levels.heights_m` est saisi ; un logement n'écrit ni l'un ni l'autre (AG-065).  En LOD 0, ignorer à l'émission, conserver dans les réglages. Compatibilité par capacité et intersections ; en V1 les trois options sont disponibles après AG-015, avec les valeurs par défaut du profil. Le registre peut ajouter une règle explicite dans une future révision. |

**Résolution.** (1) Contrôler taille, clés, types et finitude. (2) Sélectionner un profil actif exact, ou sa révision courante si aucune n'est donnée à la création. (3) Partir du profil résolu et fusionner le brouillon feuille par feuille ; les tableaux remplacent. Appliquer les chances de style aux feuilles de fonctionnalités héritées, avant les overrides. (4) Canoniser : trim, nombres de mesure en Float, champs `integer` en Integer même si le JSON écrit 1.0, champs inactifs à zéro. Si une saisie explicite donne une valeur non nulle à un champ de toit inactif, refuser. Lors d'un changement de type de toit, reconstruire le bloc avec les valeurs de ce type (plat : 0° ; deux pans/croupe : 25° ; mansarde : 25° / 65° / 0,9 m ; débord 0 m), puis appliquer les champs explicites ; à la construction des styles, chaque changement de type repart de ces valeurs. (5) Vérifier JSON effectif, limites sémantiques, règles et géométrie. Geler profondément l'objet. Au chargement, vérifier l'effectif stocké sans réappliquer les valeurs par défaut ni tirer à nouveau les chances.

**Édition.** Même profil : partir de la base enregistrée et appliquer uniquement les champs envoyés. Nouveau profil ou nouvelle révision explicite (id/révision exigés dans le brouillon d'édition dès que `profile` est présent) : conserver `name, mode, lod, seed, fidelity, footprint, levels, building_type` ; prendre façade, toit, structure, matériaux et options dans le nouveau profil ; appliquer les overrides explicites ensuite. Montrer les changements avant validation. Un changement de `count` rend une liste non vide de hauteurs incompatible tant qu'elle n'est pas ajustée ou effacée via `[]`. Sur import effectif, contrôler tous les champs, sans défauts ni migration implicite.

**Diagnostics.** `{code:"E_OPENING_CLEARANCE",severity:"error",path:"/facade/window_width_m",params:{...}}`. Chemin conforme à JSON Pointer ; ordre stable par phase puis chemin, code et identifiant de pièce. Codes : `E_SCHEMA`, `E_VERSION`, `E_PROFILE_UNAVAILABLE`, `E_HISTORICAL`, `W_HISTORICAL`, `W_DETAIL`, `E_OPENING_CLEARANCE`, `E_ROOF_GEOMETRY`, `E_BUDGET`, `E_PLAN`, `E_TARGET_STALE`, `E_CONFIRMATION_STALE`, `E_WRITE` ; pour l'assise, voir [le contrat terrain](TERRAIN_CONTRACT.md) ; pour un ensemble, [le contrat d'ensemble](ENSEMBLE_CONTRACT.md). Un avertissement permet de continuer, une erreur interdit la mutation.

**Versions.** JSON canonique : tri lexicographique des clés, UTF-8, tableaux en ordre métier, nombres finis, pas de -0. L'empreinte de géométrie exclut `name`, UUID, révision d'instance et transformation hôte ; inclut l'effectif géométrique et les révisions du moteur, profil et matériaux. L'empreinte canonique de la configuration complète conserve `name` ; elle sert au contrôle de cible, pas à la reproduction géométrique. Une révision de profil publiée est immuable et reste installée tant que la version promet de rouvrir ses bâtiments. Version future ou révision manquante : lecture limitée au diagnostic, sans écrasement. Toute migration ancienne doit être pure et testée ; elle est persistée uniquement dans une transaction réussie.
